# CLAUDE.md: retouch

## What this is
retouch is Gary's personal photo and video editor for his Pixel 9 Pro XL, installed as a PWA from GitHub Pages (jeuron-hue/retouch, public). Private working tool, not a portfolio piece. Most edits are photos of people. The 4:5 and 1080 presets are just handy sizes; Gary does not post to Instagram.

## Hard rule: photos never leave the phone
- All image processing runs on the device, in the browser. No uploads, no cloud APIs, no analytics, no telemetry.
- Enforce it, don't just promise it: a Content-Security-Policy meta tag with connect-src 'self', and a test that fails if the code contains fetch/XHR/WebSocket/sendBeacon to any other origin.
- No libraries, models or fonts from CDNs. Vendor everything into the repo so the app works fully offline after first load.
- No real photos of people in the repo. Test images that need a real person live in reference/test-images/ (gitignored). Tests that need them skip cleanly when the folder is absent.
- Every image committed to the repo (icons, synthetic fixtures) must carry no EXIF/XMP/GPS. A test checks this.

## Architecture
- Vanilla JS and CSS. No framework, no build step, no bundler, no server.
- retouch.html holds the whole app. Allowed extra files, and only these: manifest.webmanifest, sw.js, icons/, vendor/ (MediaPipe wasm and model, Mediabunny for video, fonts), and index.html as a no-script redirect stub so jeuron-hue.github.io/retouch/ opens the app. This is the minimum a PWA needs; do not split the app logic into more files. Test tooling (package.json pinning Playwright, the three test files) sits beside it; retouch_checks.cjs enforces the allowed set.
- sw.js caches the app shell and vendor/ on install so retouch works offline.
- Manifest share_target: retouch must appear in Android's share sheet, so Gary can share a photo or a video from Google Photos straight in. Handle it in the service worker. The form field is 'media' from v0.8.0; the worker also reads the old 'image' field, because Android keeps its copy of an installed app's manifest for a while after an update.
- Output goes out two ways: navigator.share with the file (straight to Instagram) and a plain download.
- Edit model: keep the original bitmap untouched. Each pixel operation produces a new bitmap on an undo/redo stack (cap the depth to protect memory). Text stays as editable overlay objects until export.
- Text and the history: every history step carries the list of text boxes as they stood after it. Applying the Text tool adds one step that reuses the previous bitmap (no new pixels, no extra memory), so undo and redo cover text like any other edit. A bitmap is released only when no step still uses it.
- Text through Crop, Resize and Add canvas: each box is carried through the same geometry as the pixels under its centre (position, size, and the turn from rotate or straighten), so it stays on the same spot of the photo at the same relative size. Flips move a box but never mirror its letters. A box whose centre falls outside the new frame is dropped from that step, with a notice; undo brings it back. Export draws the boxes into a copy of the image just before encoding, then strips and re-checks metadata as before.
- Working size: Pixel default photos are about 12 MP. Work at full resolution up to that. Larger images (50 MP mode) are downscaled to that ceiling on load with a visible notice. Keep the ceiling as one named constant.
- Load with createImageBitmap using imageOrientation 'from-image' so EXIF rotation is applied before the metadata is dropped.
- Record the pinned version of every vendored library in the file header build notes. Never upgrade one silently.

## Design
retouch has its own darkroom style. It does not use Lab Book (Gary's general design system); this section is the reference instead. Approved from a mockup on 24/10/26.
- Dark only. A neutral near-black surround so colour and skin tones are judged fairly; the photo is the brightest thing on screen. No light theme.
- Tokens (CSS custom properties at the top of retouch.html): stage #0B0B0B, chrome #141312, raised #1D1B19, pressed #2E2B27, lines #2C2925 / #3A3631, ink #EEE8DE, muted #A59E92, faint #8A8377. One accent, the amber safelight #F2A33A (text on it #1B1205). Pass #7DBE8A, watch #E0A84A, fail #E57360. The cut-out brush veil is darkroom red; the skin veil stays blue.
- Type: Barlow Semi Condensed 400/600 for labels and buttons (labels in spaced capitals), IBM Plex Mono 400/500 for numbers and edit codes, vendored in vendor/fonts/. The Text tool's own fonts are separate.
- Motifs: film-edge labels in amber mono (an edit count, "0 edit", "1 edit", "3 edits", then the date or tool name; no count on the empty screen), sprocket holes along the tool bar and the empty screen, crop-mark corners on the empty screen and the icon.
- Phone first: portrait, one-handed. Tool bar at the bottom (icon and word), image fills the rest. Pinch to zoom, drag to pan. Tap targets at least 44 px.
- Uncluttered sheets: header row is cancel (✕), title, hold-before (half circle labelled HOLD) and apply (amber ✓); no footer buttons. Status lines go in the thin strip that replaces the top bar while a tool is open. How-to text is a short caption on the photo, shown only when it applies. Figures sit in a row of cells, not a table. Text settings are split into Font, Colour and Style tabs.
- Self-host every font in vendor/ (offline requirement).

## v1 features
1. Open: JPEG, PNG, WebP, plus anything else Chrome decodes (AVIF). If decoding fails (e.g. some HEIC), say so plainly. No RAW.
2. Crop and transform: free crop, locked ratios (1:1, 4:5, 1.91:1, 9:16, 3:4, original), rotate 90, straighten slider, flip.
3. Resize: by long edge in px, with an "Instagram 1080 wide" preset.
4. Add canvas: pad the image out to a target ratio (same presets as crop) without cropping. Fill: solid colour, blurred stretch of the photo itself, or transparent. Image position adjustable inside the frame.
5. Remove background (any subject, widened 26/10/26 from people only): background means everything that is not the subject. The tool picks the subject itself, so manual work is the exception, and the status strip says what it picked. In order: (a) a person, from the selfie multiclass model (MediaPipe Tasks Vision ImageSegmenter, vendored), only if the model also sees a head (hair or face skin), since it marks bags, clothes and animals too; (b) else a plain border colour (most of the border one colour; stricter for a photographed backdrop than a flat fill), taken away by colour from the border inward, plus enclosed holes of that exact colour on a flat fill, with edge blends split back into subject colour and alpha so no fringe is left; (c) else an object from the tap-to-select model (MediaPipe InteractiveSegmenter, MagicTouch, vendored), pointed at whatever the person model marked, or the centre. A tap on the photo in view mode re-picks with the tap-to-select model. Person and object masks get edge-aware refinement; feather slider; refine brush (keep / erase) for hand fixes. Result can go on transparent, solid colour or blurred original.
6. Skin smoothing: edge-preserving filter (bilateral or guided) applied inside a skin mask built from the multiclass model's face-skin and body-skin classes. Strength slider. Blend back some original texture so it doesn't go plastic. Brush to add or remove areas from the mask.
7. Spot eraser: tap or brush over a blemish or dust spot; fill it from the surroundings. Hand-written: healing from a nearby source patch (searched by how well its surroundings match, blended in with a membrane so there is no seam), with Telea fast marching as the fallback where no source fits. Telea alone left smooth, seamed fills on skin (found on the Pixel, 24/10/26). Do not pull in OpenCV.js unless the hand-written version fails its tests. Small spots only; object removal is out of scope.
8. Text: multiple text boxes, each draggable, pinch to scale and rotate, editable until export. Font (a few vendored ones), size, colour, alignment, outline, shadow.
9. Export: JPEG (quality slider), PNG (required whenever there is transparency), WebP. Metadata is always stripped; show a one-line confirmation on export. A test parses exported JPEG/PNG/WebP bytes and fails on any EXIF, XMP, IPTC, GPS or text chunk.

Known limitation to state in the README: Pixel photos are Ultra HDR JPEGs; re-encoding drops the HDR gain map, so exports look slightly flatter on HDR screens.

## Out of scope for v1
Video (now planned as phases V1 to V4 below), object removal, any AI feature needing a network call, HEIC/RAW export, preserving Ultra HDR, batch editing, layers beyond text. Sorting photos and videos into folders is a separate app, not part of retouch (agreed 29/10/26).

## Video (planned 29/10/26)
Same rules as photos: on the phone, offline, nothing uploaded. Route: Chrome's WebCodecs (VideoDecoder, VideoEncoder, AudioDecoder, AudioEncoder) for decode and encode, with an MP4 demux and mux library vendored in vendor/ and pinned in the build notes like MediaPipe. Not ffmpeg.wasm (about 30 MB, slow on a phone, and its threads need headers GitHub Pages cannot send). Phases, easiest first, each with the usual gate:
- V1 (built as v0.8.0, 29/10/26): open and play a video (picker and share sheet), trim, sound removal, and the Video check. Trim and sound removal never re-encode: export copies the chosen packets into a new MP4, so they are fast and lossless. A copied clip must start on a keyframe, so the trim start snaps back to the keyframe at or before the chosen point (the Trim sheet says so, with a caption and a note); the end is exact to the frame. With B-frames, a frame shown after the end can come along when earlier frames are built from it; the export sheet says by how much.
- V2 (built as v0.9.0, 30/10/26): cut and join. Decisions (Gary, 30/10/26): the edit is a list of pieces, each a stretch of one of the open clips; a Cut sheet splits the piece under the playhead, deletes, reorders (Earlier, Later) and adds more videos; Trim works on the picked piece. Cuts keep the V1 rule: a split snaps back to the keyframe at or before the playhead, so the pieces still copy losslessly. Joined clips are copied when every clip has the same codec setup bytes, size, turn, frame rate and HDR or not; otherwise the whole picture is re-encoded to H.264 at the first piece's size and frame rate (measured rates within 0.5 % snap to the usual ones, so 24.93 becomes 25), other shapes scaled to fit with black bars, 0.25 bits per pixel per frame (2 to 60 Mbit/s), a keyframe every second. Piece starts still snap to keyframes when re-encoding, so a piece starts in the same place either way. Exact cuts (v0.9.1, 30/10/26): a clip from the Pixel had keyframes 4.02 s apart (an 8.55 s clip with three keyframes, likely re-saved by another app), so Split at 7.22 s cut at 4.02. When a split or a Trim start would snap back more than SNAP_OFFER (0.5 s), or there is no keyframe to snap to, the sheet offers "Split exactly at" / "Start exactly at" the frame on screen (re-encodes). A piece that starts between keyframes is the exact cut; it is found from the times alone (no flag in the recipe) and makes the export re-encode, with the reason given. The export sheet says why it re-encodes and that HDR becomes SDR, and waits for a tap on Re-encode. Sound is copied when every clip's sound setup matches; otherwise it is decoded and encoded again (AAC 48 kHz where the phone has it, else Opus), resampled by straight-line interpolation where rates differ, with silence for a clip that has none, each piece filling exactly its own length. Several videos picked or shared at once open joined, as one Join step; the service worker parks each shared file under its own key.
- V3: resolution and frame rate resampling, and canvas resize (the photo Add canvas tool, frame by frame). Reuses V2's encoder.
- V4: face smoothing. The skin model runs on every frame (about 1800 a minute at 30 fps), and the mask is steadied across frames so the skin does not flicker. Hardest, so last.

Library (chosen 29/10/26): Mediabunny 1.61.6, MPL-2.0, one file (0.7 MB, about 0.18 MB compressed), vendored byte for byte from the npm package. It reads MP4, MOV and WebM and writes MP4, copies encoded packets without decoding, and keeps rotation and colour (HDR) tags; it also has the decoders and encoders V2 to V4 need. mp4box.js (BSD-3, GPAC, clean of network code) was the alternative, but it would need a separate muxer, and mp4-muxer, the usual partner, is deprecated by its author in favour of Mediabunny. Mediabunny contains a URL reader and an HLS reader that call fetch; retouch never creates them (retouch_checks.cjs fails if retouch.html names them, or if the bundle gains new fetch calls or addresses), and the CSP blocks them anyway. It releases every few days: pin a version about two weeks old, and never upgrade silently.

Video check on the Pixel (two runs, 30/10/26 0201 and 0207 hrs; Chrome 155, Android 17, HDR screen): AAC encode works (48 kHz stereo), so re-encoded clips from V2 on keep AAC sound; Opus also works. H.264 encode works at 1080p and 4K, 30 and 60 fps. HEVC encode works at 4K (8-bit); HEVC 10-bit encode is not supported. H.264, HEVC and HEVC 10-bit decode at 4K 60 and AAC decode all work. Trial speeds (20 to 30 frames each, and they varied between the two runs, so rough): H.264 1080p 70 to 103 fps, faster than real time; H.264 4K 24 to 41 fps and HEVC 4K 26 to 44 fps, slower than real time, so re-encoding a minute of 4K 60 takes about two minutes or more. Run the check again after a Chrome or Android update before relying on these.

10-bit HDR video (confirmed 30/10/26 from a Pixel clip): the camera's 10-bit HDR setting records HEVC Main 10 with the HLG curve, sound AAC 48 kHz stereo. The test clip was portrait (1080 × 1920 after rotation), 24.93 fps, a keyframe every 1.20 s. (The check prints the codec as hev1.2.4.L123; Mediabunny labels every HEVC clip hev1, so this says nothing about the file's own box name. Exports are written as hvc1 with the clip's own setup bytes.) What V1 does with it: trim and sound removal copy the packets, so HDR stays exactly as recorded, with the frame times as recorded too. The HEVC setup (hvcC) and the colour tags (colr: primaries, transfer curve, matrix) are written into the new file, and HDR data inside the frames travels with them. Not carried: separate mdcv and clli boxes (HDR10 brightness data), which Mediabunny does not read; HLG does not use them. Chrome's own player shows the clip; if the phone cannot decode it, retouch says so and Trim and Sound still work by the numbers. Google Photos reads a trimmed export of that clip (30/10/26) as 1080 × 1920, H.265/HEVC, HLG, the same tags as the original, and it plays fine on the Pixel. Photos dates the export by its own time (the zeroed dates do not confuse it). The original carries Content Credentials (C2PA, "Media captured with a camera, Info by Google LLC"); the export does not, as with all metadata. The Pixel cannot encode HEVC 10-bit, so from V2 on a step that re-encodes an HDR clip cannot keep it HDR: it must be tone-mapped to 8-bit SDR (H.264 or HEVC), and retouch must say so before doing it. Copy-only steps (trim, sound removal) keep HDR.

Findings (V2): Mediabunny keeps only the first codec setup it is given for a track, so clips with different setup bytes cannot share a copied track: that is the test for copy or re-encode, not the frame rate alone. Sound times must never go back in its MP4 writer; at a join both sides keep the packet across the cut, so a packet that overlaps the one before by more than half is dropped, and a smaller overlap is nudged (at most about 10 ms, never adding up across joins). Its writer puts each track down in half-second chunks as it goes, so a re-encode writes the picture first and then the sound without holding the clip in memory. Its MP4 writer accepts VP8, VP9, AV1, Vorbis and the rest as they are, so the "cannot go into an MP4" path is kept but should not trigger. A re-encode draws each decoded frame through a canvas, which is where an HLG frame is turned to SDR (Chrome's own conversion); not yet seen on the Pixel. Re-encode speed in the cloud test browser (software H.264): 60 frames of 320 × 240 in about 0.5 s; check on the Pixel.

Findings (V1): exports are written to the browser's private storage (OPFS) and handed to share or download from there; memory is the fallback. The muxer stamps today's date into the MP4 headers; retouch sets every date to 0, as for photos. Phone video carries location (©xyz), make and model, and XMP; none of it is copied. The first sound packet after a cut can click faintly.

## Build order
Phase 1: shell, PWA install, share target, open/export, metadata strip, crop/transform, resize, add canvas.
Phase 2: text.
Phase 3: background removal plus refine brush.
Phase 4: skin smoothing.
Phase 5: spot eraser.
Gate at the end of each phase: each phase is built on its own branch (phase-1, phase-2, ...) and pushed to GitHub with all suites green. Gary reviews and merges to main, GitHub Pages deploys, Gary tests on the Pixel at jeuron-hue.github.io/retouch and confirms before the next phase starts. Nothing reaches main with a failing suite. No partial builds.
Builds may run in cloud sessions (claude.ai/code) or locally on the rig; both follow the same gate.
After Phase 5: the darkroom UI redesign (v0.6.0, 24/10/26). Gary then uses retouch day to day for a few months before deciding whether it becomes the final 1.0 release; fixes in that period follow the same gate.

## Testing
- retouch_checks.cjs (static): CSP present, no external origins anywhere in the source, no CDN URLs, required files present, vendored versions recorded.
- retouch_behave.cjs (behavioural): real Chromium via Playwright, since canvas and wasm need a real browser. Use synthetic fixtures generated in the test (gradients, shapes, a fake "spot") so results can be asserted numerically: crop dimensions, padding ratios, metadata absence, undo/redo, inpainting fills the spot within a colour tolerance.
- Video tests build their own synthetic clips in the test (coloured frames and a tone, encoded with WebCodecs), so durations, frame counts, sizes and the absence of an audio track can be asserted as numbers.
- Segmentation and smoothing tests run against reference/test-images/ when present and skip otherwise. Pictures without people (logos, banners, objects, pets) for trying the cut-out can be tested in a cloud session; photos of people cannot.
- retouch_mutate.sh: mutation runner over the core image functions. Survivors mean the fixtures get tightened.
- Everything green before any commit.
- Phone testing: after each merge, Gary opens jeuron-hue.github.io/retouch on the Pixel. Optional earlier check from the rig: serve locally, connect the Pixel by USB and use adb reverse so the phone opens it as localhost (a secure context for the service worker).
- Service worker updates: version the cache name in sw.js and bump it with every release, and show an "update available, reload" prompt, so the installed app on the phone never sits on a stale copy.
